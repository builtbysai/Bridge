# Bridge lockfile generation

Bridge requires two registry-generated npm lockfiles before release:

- `bridge/package-lock.json` for development, typecheck, tests, browser checks, and frontend/server builds.
- `bridge/server/package-lock.json` for the minimal production signaling runtime copied into `dist-server/`.

Do not hand-author either lockfile or invent `integrity` metadata. Generate both from the real npm registry on the reviewed Node 22 release line:

```sh
cd bridge
npm run test:lockfile-policy
npm run lockfiles:generate
```

The dependency-free lockfile policy runs in both manual Bridge workflows before registry work. The generator resolves both graphs inside a temporary workspace, pins `https://registry.npmjs.org/`, uses a private temporary `.npmrc`, disables `always-auth`, strips inherited `npm_config_*` variables and common npm/Node authentication-token variables, disables lifecycle scripts, and validates both generated lockfiles before publishing either repository destination. Publication is paired and rollback-safe so an ordinary I/O failure cannot leave one old lockfile and one new lockfile behind.

For every generated lockfile the policy requires:

1. root package identity and top-level dependency maps to match the reviewed `package.json`;
2. npm lockfile version 3;
3. every non-root package to resolve from the exact `https://registry.npmjs.org` origin, with no embedded credentials, nonstandard port, query parameters, or fragment;
4. resolved tarball paths to match the locked package identity and version, including scoped packages;
5. every resolved package to carry canonical SHA-512 integrity metadata that decodes to exactly 64 bytes and round-trips to the same base64 text; and
6. linked or unresolved package entries to fail closed.

Any deliberate future registry-mirror policy must update this reviewed boundary and its tests explicitly rather than bypassing it ad hoc.

The lockfile-mode verifier inspects executable GitHub Actions `run:` commands in both scalar and multiline blocks. In committed mode it rejects `npm run lockfiles:generate` regardless of whether the command is a one-line step or is moved into a `run: |` block; comments, environment values, and wrapper text do not satisfy or bypass the command policy. This keeps the post-adoption release boundary from silently returning to registry resolution through YAML formatting changes.

## Manual CI generation paths

The manual **Bridge CI** workflow now has two modes.

### Full validation mode

Run Bridge CI with `lockfiles_only` left at its default `false`. The workflow:

1. runs repository isolation, workflow-policy, release-preflight, and lockfile-policy checks;
2. runs `npm run lockfiles:generate` on Node 22 using the isolated public-registry configuration;
3. installs the exact generated root graph with `npm ci --ignore-scripts --no-audit --no-fund`;
4. runs the high-severity advisory gate and CycloneDX SBOM generation;
5. completes typecheck, unit/signaling integration tests, frontend/signaling builds, Chromium/Firefox/WebKit browser checks, and the disposable local-coturn relay-only test;
6. re-runs both `verify:committed-lockfiles` and `verify:lockfiles-handoff` after the dependency-backed/browser/TURN sequence so the final artifact bytes and their source-revision binding cannot have drifted during validation; and
7. only after those final integrity checks succeed, uploads the pair as the `bridge-lockfiles` workflow artifact.

The post-validation `bridge-lockfiles` artifact remains the preferred evidence for committing the final pair because it proves the complete Bridge validation suite used that exact generated dependency graph and that the published lockfile bytes still match the source-bound handoff manifest at the artifact boundary.

### Lockfile-only handoff mode

Run Bridge CI manually with `lockfiles_only=true` when the immediate goal is to obtain an authentic registry-generated pair for repository review, especially when a later dependency-backed/browser step is preventing the full job from reaching its final artifact upload.

This bounded 10-minute job still performs the Bridge-only scope guard, workflow security/timeout/runner/retention guards, lockfile-mode and supply-chain checks, release preflight, and the complete dependency-free lockfile policy suite before touching the registry. It then generates both lockfiles through the same isolated helper, re-runs `verify:committed-lockfiles` against the generated pair, and uploads both files together as `bridge-generated-lockfile-pair` with seven-day retention.

`bridge-generated-lockfile-pair` is a **handoff artifact, not release-validation evidence**. It establishes that the bytes were generated by the reviewed Node/npm path and satisfy repository provenance/integrity policy; it does not claim `npm ci`, audit, typecheck, Vitest, builds, Playwright, or coturn passed against that graph. After the pair is committed, the full dependency-backed validation sequence still has to pass before release.

This distinction is intentional: it makes the highest-priority lockfile blocker independently retrievable without weakening or moving the existing post-validation `bridge-lockfiles` publication boundary.

### Lockfile handoff checklist

- [x] Generate both lockfiles together through the isolated credential-free public-registry helper.
- [x] Provide a bounded lockfile-only CI path that can publish a provenance-validated pair even if unrelated later validation is unavailable.
- [x] Keep the `bridge-lockfiles` release-review artifact after the full manual CI validation sequence.
- [x] Re-verify the generated pair and source-bound handoff manifest immediately before the fully validated artifact is uploaded.
- [x] Guard both scalar and multiline workflow `run:` commands so committed-lockfile mode cannot hide on-the-fly regeneration behind YAML block formatting.
- [x] Block Bridge Deploy release-artifact production unless both reviewed repository lockfiles are already present and policy-valid.
- [ ] Download both lockfiles from the same workflow run and review the resolved transitive graphs together.
- [ ] Commit `bridge/package-lock.json` and `bridge/server/package-lock.json` together.
- [ ] Remove temporary on-the-fly generation from CI/deploy after the committed pair lands, and make release preflight require the committed files.
- [ ] Run the complete dependency-backed validation suite against the committed pair.

When reviewing the pair, confirm that the root lockfile reflects the exact top-level versions pinned in `bridge/package.json`, the signaling lockfile contains only the production runtime tree rooted at `ws`, the transitive package set is expected, and no unexpected optional/platform-specific package materially broadens the runtime or build trust boundary.

## Release artifact path

The manual **Bridge Deploy** workflow is now fail-closed during bootstrap mode. Before it can generate or upload any `bridge-release` artifact, it executes `npm run verify:committed-lockfiles -- --require-present`. If either reviewed repository lockfile is absent, partially committed, or violates the registry/integrity policy, the release artifact build stops before registry-backed dependency installation or production build work.

CI remains the only bootstrap path allowed to generate a lockfile pair for handoff/review. This separation prevents a deploy artifact from being treated as release-ready evidence while its dependency graph still comes from transient resolution.

The Deploy workflow still contains the temporary generation/install sequence because the committed-mode transition must be atomic with the lockfile adoption: once both repository lockfiles land, `verify:lockfile-mode` requires removing on-the-fly generation before the workflow can proceed. At that point Bridge CI and Bridge Deploy must consume the committed files exclusively. Keep `npm ci --ignore-scripts --no-audit --no-fund` for the Bridge build graph and `npm ci --omit=dev --ignore-scripts --no-audit --no-fund` for the packaged signaling runtime, and update `scripts/release-preflight.mjs` at the same transition so release validation requires both committed files.

A generated lockfile in a CI handoff artifact is not a substitute for a reviewed committed lockfile. Until the pair is committed, a later registry resolution can still select a different transitive graph permitted by upstream metadata, which is why Deploy now refuses to publish a release artifact in that state.

Lockfile generation does not require production hosting, signaling, TURN, or operator credentials. It does require a functioning npm registry connection; an environment that cannot reach the registry cannot safely synthesize this release evidence.
