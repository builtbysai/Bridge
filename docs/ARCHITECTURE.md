# Architecture

## Components

```text
Browser A                       Browser B
   |                               |
   +------ HTTPS/WSS signaling ----+
   |                               |
   +======== WebRTC DataChannel ===+
                 |
          STUN / TURN fallback
```

The signaling service exchanges ephemeral session metadata, SDP descriptions, and ICE candidates. Transfer payload bytes do not pass through the signaling service.

## Session lifecycle

1. The host creates a 256-bit random pairing secret in the browser.
2. The browser derives a SHA-256 rendezvous verifier and sends only that verifier to signaling.
3. Signaling creates a short-lived session ID and associates the verifier with the host socket.
4. A QR/link carries the session ID in the query string and the raw pairing secret in the URL fragment.
5. The joiner derives the same verifier and uses it only for signaling admission.
6. Peers exchange SDP/ICE through signaling and establish a WebRTC DataChannel.
7. Both browsers perform session/role-bound HMAC key confirmation over the DataChannel using the raw pairing secret. Transfer code does not receive the channel until the expected peer proof verifies.
8. The browsers derive the transfer key independently with HKDF-SHA-256 and begin application-encrypted transfers.
9. Connection interruption enters bounded WebRTC recovery. Replacement DataChannels repeat key confirmation before transfer resume negotiation is allowed.
10. Host disconnect, explicit host close, server shutdown, or TTL expiry closes the ephemeral rendezvous session.

## Transfer protocol

Control messages are versioned JSON validated at runtime. Payload chunks are binary and are processed serially in arrival order.

Current controls:

```text
transfer-offer
transfer-accept
transfer-reject
transfer-cancel
transfer-complete
transfer-verified
transfer-resume-query
transfer-resume-state
request-item
request-decline
```

The DataChannel pairing handshake uses a separate `bridge-key-confirm` control before `TransferEngine` is attached.

Binary chunks contain:

- transfer ID length
- UTF-8 transfer ID
- 32-bit chunk index
- AES-GCM ciphertext and authentication tag

The transfer ID and chunk index are also bound into AES-GCM associated data. Each transfer uses a fresh random nonce prefix; the chunk index completes the per-chunk IV. The receiver requires exactly the next expected index, decrypts and writes each chunk before processing the next message, updates incremental SHA-256 state, and acknowledges completion only after the advertised size and digest verify.

The sender respects `RTCDataChannel.bufferedAmount`, pauses at the configured high-water mark, and resumes after the low-water notification. Approval, completion verification, backpressure, and channel-recovery waits are bounded so a lost peer does not leave an operation pending forever.

## Resume and cancellation

The receiver owns the authoritative verified resume boundary. After a replacement authenticated DataChannel opens, the sender asks for `transfer-resume-state` and resumes from the receiver's next verified chunk index. Completed receives can answer the same query as already complete, covering a lost final acknowledgement.

Cancellation is end to end. A sender receives an outbound transfer handle before hashing finishes, so queue cancellation can stop hashing, approval wait, transmission, or verification. Receiver corruption/order/storage failures abort the sink and propagate `transfer-cancel` to the sender.

## Security

WebRTC DataChannels already use DTLS. Bridge adds an application layer so signaling compromise cannot silently substitute a peer without detection and so transfer confidentiality/integrity does not depend solely on the transport session.

- QR pairing secret: 256 random bits generated by Web Crypto.
- Signaling admission: SHA-256 verifier only; raw pairing secret is not sent to signaling.
- Peer authentication: HKDF-derived HMAC-SHA-256 proof bound to session ID and explicit host/guest role.
- Transfer key derivation: HKDF-SHA-256.
- Payload encryption: AES-256-GCM per chunk.
- Integrity: AEAD per chunk plus full-payload SHA-256.
- Transfer/control identifiers and metadata are runtime validated and bounded before state is allocated.
- Typed short codes are rendezvous identifiers only until a PAKE/equivalent authenticated design is implemented.
- No normal transfer payload is stored by the backend.

## TURN

TURN is required for production reliability. Direct P2P is preferred, but restrictive NAT/firewall environments may force relay traffic through TURN.

The UI exposes the selected route:

- **Direct** — the selected ICE candidate pair does not contain a relay candidate.
- **Relayed** — the selected pair contains a relay candidate.

Relay-only privacy mode sets `iceTransportPolicy: "relay"` and fails closed when no usable TURN configuration exists. Browser-exposed static TURN credentials must not be long-lived production shared secrets; production should prefer short-lived operator-issued credentials.

## Large files

The sender hashes and reads `File` slices incrementally rather than materializing an entire file. Receiver storage is selected progressively:

1. File System Access writable stream where supported and user-approved.
2. Bounded in-memory receive for payloads within the reviewed browser-memory limit.
3. Larger payloads require a streaming/direct-to-disk path rather than unbounded Blob accumulation.

Receive sink state, incremental hash state, and verified chunk position are retained across replacement DataChannels for resumable transfers.

## PWA boundary

The PWA service worker is registered from an external module so the production `script-src 'self'` CSP does not require `unsafe-inline`. Bridge cache cleanup is namespace-scoped to Bridge-owned cache names and must not delete Cache Storage belonging to sibling applications on a shared origin.

## Deployment boundary

The frontend can be statically hosted. Signaling and TURN are separate runtime services. Production must set the exact allowed frontend origin on signaling and narrow frontend CSP `connect-src` to the selected signaling origin. Repository workflows must operate only on `bridge/**` and the dedicated Bridge workflow files and must never build or deploy sibling projects.
